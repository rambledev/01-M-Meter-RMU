# Requirement — RMU Meter Collection

> เอกสารนี้สรุป requirement ที่ได้รับจากผู้ใช้ (2026-09-01) เพื่อเป็นข้อมูลอ้างอิงร่วมกันก่อนเริ่ม coding
> Tech stack ทั้งหมดถูกอนุมัติและล็อกแล้วเมื่อ 2026-09-02 — ดู [tech-stack.md](tech-stack.md) และ [decision-log.md](decision-log.md)

## 1. ภาพรวมระบบ

ระบบบันทึกค่ามิเตอร์ไฟฟ้า (RMU Meter Collection) สำหรับหน่วยงาน/หอพัก โดยมีคุณสมบัติหลัก:

- **Mobile First** — ออกแบบ UI/UX ให้ใช้งานบนมือถือเป็นหลัก (ผู้จดมิเตอร์เดินถือมือถือไปตามจุดต่างๆ)
- **Offline First** — ต้องบันทึกข้อมูลได้แม้ไม่มีสัญญาณอินเทอร์เน็ต แล้ว sync อัตโนมัติภายหลัง

## 2. Role (3 บทบาท)

| Role | หน้าที่หลัก (สันนิษฐานจากบริบท workflow ที่ให้มา — ยังไม่ได้ระบุรายละเอียดสิทธิ์ชัดเจน) |
|---|---|
| `ADMIN` | จัดการ Meter/Room/Zone, ดู/Export รายงาน, จัดการ Sync error |
| `METER_READER` | ผู้จดมิเตอร์ — ทำ workflow หลัก: scan → ถ่ายภาพ → OCR → confirm → บันทึก |
| `RESIDENT` | ผู้พักอาศัย — สันนิษฐานว่าดูข้อมูลการใช้ไฟของตนเอง (ยังไม่ระบุขอบเขตชัดเจน ต้องยืนยันเพิ่มเติม) |

**MVP Demo**: ยังไม่ทำ Login จริง — ใช้การ "เลือก Role" เพื่อจำลองการใช้งานแทน

## 3. Business Rules ที่ระบุชัดเจน

### 3.1 เดือนของ Reading
- ทุก Reading ต้องผูกกับเดือน (month)
- หลัง Scan QR ระบบเลือกเดือนปัจจุบันให้อัตโนมัติ
- ผู้ใช้สามารถเลือกย้อนหลังได้
- **ห้ามเลือกเดือนในอนาคต**
- Previous Reading ต้องอ้างอิงจาก **เดือนก่อนหน้าของเดือนที่เลือก** (ไม่ใช่แค่ "ครั้งล่าสุดที่บันทึก") — เช่นถ้าเลือกย้อนหลังไปเดือน มี.ค. ต้องดึงค่าของ ก.พ. มาเทียบ ไม่ใช่ดึงค่าล่าสุดที่มีในระบบ

### 3.2 Duplicate Prevention
- ห้ามบันทึกข้อมูลซ้ำสำหรับ **Meter + Month** เดียวกัน
- ต้องตรวจสอบก่อน Confirm ทุกครั้ง (ทั้งกรณี online และกรณี sync จาก offline queue)

### 3.3 OCR
ต้องเก็บข้อมูล 4 ส่วนแยกกันเสมอ:
1. **Original Image** — ภาพมิเตอร์เต็มภาพ (ใช้เป็นหลักฐานอ้างอิง)
2. **OCR Region** — บริเวณที่ครอปมาเฉพาะเลขมิเตอร์
3. **OCR Value** — ค่าที่ OCR อ่านได้ดิบๆ
4. **Confirmed Value** — ค่าที่ผู้จดตรวจสอบ/แก้ไขแล้วยืนยัน

ผู้จดต้องแก้ไขค่า OCR ได้เสมอก่อน confirm (OCR ไม่ใช่ค่าสุดท้าย)

### 3.4 Offline & Sync
- ใช้ IndexedDB เก็บข้อมูล + รูปภาพเมื่อ offline (แนะนำ Dexie.js เป็น library ครอบ — ดู decision-log.md)
- มี Sync Queue พร้อม status: `DRAFT → PENDING_SYNC → SYNCING → SYNCED` หรือ `SYNC_ERROR`
- กลับมา online แล้วต้อง sync อัตโนมัติ ไม่ต้องให้ผู้ใช้กดเอง

### 3.5 Export
- Export เป็น Excel ตามรูปแบบตัวอย่างรายงาน (ยังไม่ได้รับไฟล์ตัวอย่างจริง — ต้องขอเพิ่ม)
- คอลัมน์ที่ต้องมี พร้อม group header ตามที่กำหนด (ดูรายละเอียดใน workflow.md §Export)
- **สูตรคำนวณค่าไฟ (ค่าไฟพื้นฐาน / ค่า FT / ภาษี / รวมทั้งสิ้น) ยังไม่ final — ห้ามเดาสูตร** ต้องรอข้อมูลจากผู้ใช้ก่อนเริ่มพัฒนาส่วนคำนวณ

## 4. UX Principle (สำคัญที่สุดตามที่ผู้ใช้ระบุ)

> "ขั้นตอนน้อยที่สุด ใช้งานง่ายที่สุด"

- ผู้จด **ไม่ควรกรอกข้อมูลที่ระบบรู้อยู่แล้ว**
- QR ต้องระบุ Meter ได้ทันที ระบบต้องรู้ Room/Zone ที่ผูกกับมิเตอร์นั้นเอง (ไม่ต้องเลือกเอง)
- ต้องแสดง Previous Reading ให้เห็นทันทีหลัง scan
- เดือนปัจจุบันเลือกอัตโนมัติ (แก้ได้)
- OCR ช่วยกรอกค่าให้ ผู้จดมีหน้าที่แค่ตรวจสอบและ confirm

เป้าหมาย flow: **Scan → ถ่าย → ตรวจ → ยืนยัน → จบ** (ให้น้อย step ที่สุดเท่าที่ business rule ยังครบ)

## 5. สิ่งที่ยังไม่ชัดเจน / ต้องยืนยันเพิ่มเติมจากผู้ใช้

รายการนี้ไม่ใช่การเดา — เป็นการรวบรวมช่องว่างที่พบระหว่างวิเคราะห์ requirement เพื่อถามผู้ใช้ในรอบถัดไป (ต่างจากประเด็น tech stack ซึ่งถูกอนุมัติปิดรอบแล้วใน decision-log.md):

1. **สูตรคำนวณค่าไฟ** (ค่าไฟพื้นฐาน, ค่า FT, ภาษี) — ต้องได้สูตร/อัตราจริงก่อนพัฒนา Phase 6 (Excel Export) (ดู [export-format.md](export-format.md))
2. **ไฟล์ตัวอย่างรายงาน Excel จริง** — เพื่อ mapping format/สไตล์ให้ตรงเป๊ะ (merge cell, group header ฯลฯ) (ดู [export-format.md](export-format.md))
3. **ขอบเขตสิทธิ์ของแต่ละ Role** โดยเฉพาะ `RESIDENT` เห็นข้อมูลระดับไหน (เฉพาะห้องตัวเอง? ทั้ง zone?) และ `ADMIN` vs `METER_READER` มีสิทธิ์แก้ไข reading ที่ confirm แล้วหรือไม่ (ดู [data-model.md](data-model.md) §Role)
4. **OCR provider/engine** — จะใช้ on-device OCR (เช่น ML Kit, Tesseract.js) หรือเรียก API ภายนอก (มีผลต่อเรื่อง offline-first เพราะถ้า OCR ต้องพึ่ง API ภายนอก จะ OCR ไม่ได้ตอน offline) — ดูตัวเลือกที่วิเคราะห์ไว้ใน [ocr-strategy.md](ocr-strategy.md)
5. **QR Code**: ใครเป็นคนสร้าง/พิมพ์ QR ติดที่มิเตอร์ — ระบบนี้ต้องมีหน้า generate QR ด้วยหรือไม่ หรือมีระบบอื่นทำอยู่แล้ว
6. **จำนวนผู้ใช้พร้อมกันโดยประมาณ** และขนาดข้อมูล (จำนวนมิเตอร์/zone) เพื่อประกอบการออกแบบ database/infra
